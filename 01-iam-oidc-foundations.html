1. Zero-knowledge explanation

📘 Beginner Concept — the hotel

Authentication (AuthN) is the front desk checking your passport: “Who are you?” Authorization (AuthZ) is the key card that only opens your room and the gym: “What may you do?” A reverse proxy is the hotel lobby — every guest and delivery goes through it, and staff decide who gets past. An identity broker is a concierge who accepts your passport from another country's desk (an upstream identity provider) and hands you the hotel's own key card.

OAuth 2.0 vs OpenID Connect

OAuth 2.0 is a framework for delegated authorization: it answers “may this app call that API for this user?” by issuing an access_token. It deliberately says nothing about who the user is. OpenID Connect (OIDC) is a thin identity layer on top: adding the openid scope makes the server also return an id_token (a JWT stating who authenticated, when, and how) plus a /userinfo endpoint and discovery metadata.

Anatomy of a JWT

A JSON Web Token is three Base64URL strings joined by dots: header.payload.signature.

// header
{ "alg": "RS256", "kid": "key-2025-01", "typ": "JWT" }
// payload (claims)
{ "iss": "https://test.partnerlink.enterprise.com/mga/sps/oauth/oauth20/metadata/PartnerLink_OIDC_Test",
  "sub": "jdoe", "aud": "<partner_portal_clientid>",
  "exp": 1767225600, "iat": 1767222000, "nonce": "n-0S6_WzA2Mj", "acr": "urn:partnerlink:mfa" }
// signature = RSA-SHA256(base64url(header) + "." + base64url(payload), ciam_private_key)
Note
The JWT payload is encoded, not encrypted. Anyone holding the token can read it. The signature only proves it hasn't been altered and who issued it.

JWKS — how a signature is verified without sharing a secret

The issuer signs with a private key it never shares. It publishes the matching public keys as a JSON Web Key Set (/jwks/PartnerLink_OIDC_Test). The token header's kid says which key to use. The backend downloads the JWKS (cached), finds the key, verifies the signature, then checks iss, aud, exp and nonce.

Identity brokering

Brokering means the authorization server does not authenticate users itself: it redirects to another IdP, trusts the result, and issues its own tokens to the client. The client only ever trusts one issuer (ciam), no matter how many upstream IdPs exist behind it.

2. High-level architecture

🏗️ Architecture Deep Dive — why a code, not a token, in the URL?
URLs end up in browser history, proxy logs and Referer headers. So the AS returns a short-lived, single-use authorization code in the URL, and the confidential backend swaps it for tokens on a private back channel, authenticating with its client_secret.
