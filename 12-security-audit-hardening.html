12 · Security Audit & Hardening Blueprint

Five findings against the current ciam design, each explained from first principles, with the attack it enables, the exact fix and a test that proves the fix.

1. Zero-knowledge explanation

📘 Beginner Concept — why these controls exist

state is a random ticket number you attach to a request and must get back unchanged — it proves the response belongs to your request (stops login CSRF). nonce is a random value baked into the token so an old token can't be replayed. PKCE proves the one who redeems the code is the one who asked for it. Exact redirect matching and URL-encoding make sure codes go only where intended. Correct iss proves who minted the token. Network gates (Akamai/ACL) should block everything except what must be public.

2. High-level architecture — before vs after

🏗️ Architecture Deep Dive — two relationships, two sets of protections
ciam is an authorization server to the portal and a relying party to csl. As a relying party it must behave like any client: its own state, nonce and PKCE verifier toward csl. As an authorization server it must enforce the portal's PKCE challenge and exact redirect_uri.

4. Environment deep dive — findings in detail

Finding 1 — state & nonce isolation

Attack: an attacker who can start a login on csl with the portal's known state=789 (or fixed value) can feed a victim a callback that ciam accepts because the value matches nothing ciam generated — login CSRF / session fixation. Reusing the portal's value also leaks it to csl and its logs.

Fix: generate 256-bit random state2/nonce2 in InfoMap_partnerLoginRedirect.js, store in session, verify and delete on return (code in Module 09), and restore the portal's original state only in the final redirect.

# test: replay the return step with a tampered state — must fail
curl -sI -H "Cookie: PD-S-SESSION-ID=$SID" \
 "https://test.partnerlink.enterprise.com/mga/sps/oauth/oauth20/authorize?client_id=$CID&scope=openid&state=attacker" | egrep -i '^(HTTP|location)'
# expected: error, not a redirect carrying a code

Finding 2 — PKCE S256

Attack: anyone who captures the code (browser extension, referrer, shared device, logs) can redeem it if they also know/steal the client secret or if the client is public. PKCE binds the code to the original requester.

Fix: require code_challenge with S256 on both /authsvc and /authorize; reject plain; verify code_verifier at /token; advertise code_challenge_methods_supported:["S256"]. Test without a challenge: must return invalid_request.

Finding 3 — Nested URL encoding

Current: /authb/login?appId=27096415/authorize?appId=123&scope=openid&state=789. A second ? is not a delimiter; parsers differ, so parameters can be lost, swapped or injected (appId appears twice).

Fix: /authb/login?appId=27096415&redirect_uri=https%3A%2F%2Ftest.partnerlink.enterprise.com%2Fmga%2Fsps%2Foauth%2Foauth20%2Fauthorize%3Fclient_id%3D…%26state%3D… — one ?, every nested value percent-encoded, and csl must exact-match the redirect_uri.

curl -sI "https://test.partnerlink.enterprise.com/mga/sps/authsvc?client=$CID&scope=openid&state=1" \
 | grep -i '^location:' | tr -cd '?' | wc -c      # expect 1

Finding 4 — localhost issuer and ROPC

Risk: internal Provider ID https://localhost/sps/oauth/oauth20/15 makes validators fail or be loosened; ROPC lets clients collect passwords and bypass upstream MFA.

Fix: Provider ID to the external URL, update every relying party; untick “Resource owner username password” (and Implicit); deploy; confirm unsupported_grant_type (Module 05).

⚠️ Security Pitfall — more hardening items to check
  • client_secret in a vault; rotate; never in the SPA.
  • Short lifetimes: code ≤ 60 s single-use, access ≤ 15 min, id_token ≤ 10 min.
  • Secure; HttpOnly; SameSite on PD-S-SESSION-ID; HSTS and TLS 1.2+.
  • No tokens/secrets in trace logs; turn tracing off after use.
  • Validate iss, aud, exp, nonce, alg pinned to RS256 (reject none).
