06 · OAuth/OIDC Clients & PKCE

How an application becomes known to ciam: client registration, the confidential/public distinction, why redirect_uri must match exactly, and how PKCE (S256) protects the authorization code.

1. Zero-knowledge explanation

📘 Beginner Concept — the guest list and the claim ticket

Client registration is the guest list: the bouncer (ciam) only serves apps that were registered, and only sends them to the address they registered. A confidential client can keep a secret (a server like partner_portal_backend); a public client cannot (a browser SPA or mobile app — anyone can read its code).

PKCE (“pixy”) is a claim ticket: when you drop off a coat you keep half of a torn ticket (code_verifier); the cloakroom keeps a fingerprint of it (code_challenge). Only the person holding the original half can collect the coat, even if someone steals the cloakroom slip (the authorization code).

  • client_id: public name, <partner_portal_clientid>. client_secret: password for confidential clients, sent only on the back channel.
  • redirect_uri: where the code is returned. Must be pre-registered and compared exactly (scheme, host, port, path, query) — no wildcards, no prefix matching.
  • PKCE: code_challenge = BASE64URL(SHA256(code_verifier)), method S256. plain is insecure and should be refused.

2. High-level architecture

🏗️ Architecture Deep Dive — defence in depth for the code
Even confidential clients should use PKCE today (OAuth 2.0 Security BCP, OAuth 2.1): client_secret authenticates the backend, PKCE binds the code to the specific login transaction, defeating code injection and interception.

3. Low-level technical sequence — authorization code with PKCE

Generate a PKCE pair (for tests)

VERIFIER=$(openssl rand -base64 48 | tr -d '=+/\n' | cut -c1-64)
CHALLENGE=$(printf %s "$VERIFIER" | openssl dgst -sha256 -binary | openssl base64 -A | tr '+/' '-_' | tr -d '=')
echo "verifier=$VERIFIER"; echo "challenge=$CHALLENGE"

# authorize (open in browser)
echo "https://test.partnerlink.enterprise.com/mga/sps/authsvc?client=<partner_portal_clientid>&scope=openid&state=abc&nonce=xyz&code_challenge=$CHALLENGE&code_challenge_method=S256"

# exchange
curl -s -X POST https://test.partnerlink.enterprise.com/mga/sps/oauth/oauth20/token \
  -d grant_type=authorization_code -d code="$CODE" \
  -d redirect_uri=https://portal.example.com/cb \
  -d client_id=<partner_portal_clientid> -d client_secret="$SECRET" \
  -d code_verifier="$VERIFIER"

Registering the client in LMI (verify menu names)

  1. Secure Access Control → API Protection → Definitions → PartnerLink_OIDC_Test → Clients → Add.
  2. Set Client ID, Client secret (long, random, stored in a vault), Client type = Confidential.
  3. Add Redirect URIs: exact HTTPS URLs, one per environment. Never http:// (except localhost in dev) and never wildcards.
  4. Restrict allowed grant types/scopes (openid, plus only needed scopes).
  5. Enable PKCE requirement if your firmware exposes it; otherwise enforce in the pre-token/authorize rule (see Module 09).
  6. Deploy pending changes.

⚠️ Security Pitfall — open redirect via loose matching
If the server accepts redirect_uri by prefix or ignores the query, an attacker registers nothing but crafts https://portal.example.com/cb/../evil or a sibling path, receives the code, and takes over the account. Strict exact matching plus PKCE closes this.
