1. Zero-knowledge explanation

📘 Beginner Concept — owning a generator vs buying electricity

Running ISVA is like running your own power generator: you patch it, tune it, deploy changes, and write custom code to make it fit. IBM Security Verify is the utility company: same electricity (OIDC tokens), no generator room. You trade custom code for configuration; where configuration can't express your logic, you call out to a small service you host (a webhook).

  • Tenant: your private instance, https://<tenant>.verify.ibm.com.
  • Application: a registered OIDC client (replaces definition + client).
  • Identity Source: where users authenticate — the tenant's cloud directory or a federated IdP such as csl.
  • Access policy: rules deciding allow / deny / require MFA.
  • Attribute mapping & functions: which profile data becomes which claim.
  • Webhooks: HTTPS calls from Verify to your service (pre-token enrichment, event notifications).

2. High-level architecture — 1-to-1 component mapping

🏗️ Architecture Deep Dive — what changes for the portal
For partner_portal and partner_portal_backend the migration is a configuration change: a new issuer/discovery URL, new client_id/secret, and new endpoints. If the backend uses a standards-compliant OIDC library with discovery, it's mostly one URL.

⚠️ Security Pitfall — migration risks
  • Issuer change: iss/aud change, so old tokens won't validate on the new backend config — run both validators during the pilot.
  • User identifiers: ensure sub is stable (use the same attribute as before) or accounts will fork.
  • Secrets: new client secret in a vault; do not reuse the legacy secret.
  • Webhook endpoints are new attack surface: authenticate, rate-limit, validate payloads, allowlist claims.
  • Data residency / privacy: confirm tenant region and attribute minimisation.

Migration plan

  1. Inventory: clients, redirect URIs, scopes, claims consumed (decode real tokens), rule behaviours, WebSEAL ACLs.
  2. Fix first: apply Module 12 hardening on legacy so the baseline is sound.
  3. Build: tenant, csl identity source, application, mappings, policies; capture as scripts/APIs.
  4. Test: run the curl suite and HAR comparison (Module 14) against both issuers.
  5. Pilot: feature-flag a small cohort; monitor errors, latency, MFA prompts.
  6. Cut over, keep legacy read-only for a rollback window; then decommission ciam and close Akamai/ACL exceptions.
