Glossary

Every acronym and concept used on this site, in plain English, with a pointer to where it is explained in depth.

Terms

AAC — Advanced Access Control
The ISVA module that adds risk-based access, OAuth/OIDC provider and the authentication service on top of WebSEAL.See Module 03
Access token
A short-lived credential an API accepts as proof that a client may act for a user. Format may be opaque or a JWT.Module 01, 05
ACL — Access Control List
In WebSEAL: who (user, group, unauthenticated, any-other) may do what (T r x m …) on an object in the protected object space. Inherited downward unless overridden.Module 02
Akamai EdgeSuite
The CDN/WAF in front of WebSEAL. Applies IP allowlists, bot and WAF rules. Block pages reference errors.edgesuite.net and a Reference #.Module 02, 07
API Protection Definition
The server-side rulebook for an OAuth/OIDC authorization server in ISVA: grants, lifetimes, issuer, keys, mapping rules, clients. Here: PartnerLink_OIDC_Test.Module 05
Authentication vs Authorization
AuthN: proving who you are. AuthZ: deciding what you may do.Module 01
authsvc — Authentication Service
The runtime endpoint /mga/sps/authsvc that executes authentication policies made of mechanisms.Module 08
Authorization code
A short-lived, single-use value returned through the browser and exchanged by the backend at /token for tokens.Module 11
Back channel / Front channel
Front channel: messages relayed by the browser through redirects (visible, tamperable). Back channel: direct server-to-server TLS, where secrets may travel.Module 01
Identity broker
A server that authenticates users by delegating to another identity provider and then issues its own tokens. Here ciam brokers csl.Module 01
CBA — Context-Based Access
Policy decisions using request context (IP, device, geo, risk score) that can permit, deny or require step-up.Module 03
ciam
Placeholder name for the identity broker / authorization server running on ISVA.
Client (relying party)
An application registered with an authorization server. Confidential clients keep a secret; public clients cannot.Module 06
client_secret
Password of a confidential client, sent only on the back channel. Store in a vault; rotate.
code_verifier / code_challenge
PKCE pair. Challenge = BASE64URL(SHA-256(verifier)). Challenge goes on the authorize request, verifier on the token request.Module 06
csl
Placeholder name for the upstream identity provider that performs password + MFA.
Discovery (metadata)
A public JSON document listing issuer, endpoints and supported features of an OpenID provider.Module 07
HAR
HTTP Archive: a browser recording of requests/responses, used to debug redirects and cookies. Contains secrets, so sanitize it.Module 14
ID token
A JWT issued by an OpenID provider asserting who authenticated, when and how (iss sub aud exp iat nonce acr amr).
InfoMap
An authentication mechanism type that runs a JavaScript rule. InfoMap_partnerLoginRedirect.js redirects to csl.Module 09
iss (issuer)
JWT claim naming who minted the token. Must equal the issuer the relying party expects. In ISVA it comes from the Provider ID.Module 05
iv-user / iv-creds
HTTP headers WebSEAL injects across a junction: the user name and a Base64 credential blob.Module 02
Junction
A mapping from a WebSEAL URL prefix (e.g. /mga) to a back-end server.Module 02
JWKS
JSON Web Key Set: the issuer's public signing keys, selected by kid.Module 07
JWT
JSON Web Token: header.payload.signature, Base64URL-encoded and signed (readable by anyone).Module 01
kid
Key ID in a JWT header identifying which JWKS key verifies the signature.
LMI — Local Management Interface
Admin web console and REST API of the appliance (port 9443). Changes are staged until deployed.Module 04
Mapping rule
Server-side JavaScript (Rhino) hook that customises authentication or token generation.Module 09
MFA / step-up
Requiring an additional factor, either at login or when a sensitive resource demands stronger assurance.
nonce
Random value tied to an authentication request and copied into the ID token to prevent replay.
OAuth 2.0
Framework for delegated authorization using tokens.
OIDC — OpenID Connect
Identity layer on OAuth 2.0 adding the ID token, openid scope, /userinfo and discovery.
pdadmin
CLI of the policy server for junctions, ACLs, POPs and the object space.Module 04
PD-S-SESSION-ID
WebSEAL session cookie: an opaque handle to a server-side session.
PKCE
Proof Key for Code Exchange: binds an authorization code to the client that requested it. Require S256.Module 06
POP — Policy of Protection
Extra conditions on an object: IP restrictions, time of day, quality of protection, audit level, step-up attributes.
POS — Protected Object Space
The tree of objects WebSEAL protects, to which ACLs and POPs attach.
Provider ID
The issuer identifier configured on an API Protection Definition; becomes iss.
redirect_uri
Pre-registered callback where the authorization code is delivered; must match exactly.
Refresh token
Long-lived credential used to obtain new access tokens without user interaction. Rotate and protect.
Rhino
Java-based JavaScript engine (ES5) used for ISVA mapping rules.
ROPC
Resource Owner Password Credentials grant: the app collects the password. Deprecated and insecure; disable.Module 05
scope
Space-separated list of permissions requested; openid turns OAuth into OIDC.
state
Random value echoed back unchanged to bind a response to its request (CSRF defence). Each OAuth leg needs its own.Module 12
STSUU
Security Token Service Universal User: XML/JS structure with Principal, AttributeList and ContextAttributes, carried through token rules.Module 10
Tenant
Your private instance of IBM Security Verify: https://<tenant>.verify.ibm.com.Module 13
Webhook
An HTTPS callback from Verify to a service you host (pre-token enrichment, event notification).
WebSEAL
ISVA's reverse proxy: TLS termination, sessions, ACL/POP enforcement, junctions.Module 02
