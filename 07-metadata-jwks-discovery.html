07 · Metadata & JWKS Discovery

How partner_portal_backend learns where the endpoints are and which public key verifies a signature — and why a single misconfigured ACL or CDN rule on these two URLs breaks every login.

1. Zero-knowledge explanation

📘 Beginner Concept — the phone book and the notary's stamp sample

Metadata (discovery) is a phone book entry published by ciam: “my authorize address is…, my token address is…, my name is…”. JWKS is the notary's specimen stamp: anybody may look at it to confirm that a document was truly stamped by ciam. Because these two documents are public by design and contain no secrets, they must be reachable without logging in — otherwise nobody can verify anything.

  • /mga/sps/oauth/oauth20/metadata/PartnerLink_OIDC_Test — JSON document (OpenID Provider Configuration).
  • /mga/sps/oauth/oauth20/jwks/PartnerLink_OIDC_Test — JSON Web Key Set (public keys only).
  • kid (key ID) in the token header selects the key; rotation publishes a new key alongside the old one.

2. High-level architecture

🏗️ Architecture Deep Dive — cache and refetch
Backends fetch metadata at start-up and JWKS on first use, then cache. When a token arrives with an unknown kid, a well-behaved library refetches the JWKS once (rate-limited). If the endpoint is blocked at that moment, all new tokens fail validation even though old ones still work — a classic delayed outage after key rotation.

Key rotation procedure (overlap, never cut-over)

  1. Create/import a new signing key pair in LMI (SSL Certificates → runtime keystore, e.g. rt_profile_keys; verify keystore name on your version) with a new label.
  2. Publish both keys in JWKS: add the new certificate to the definition's key configuration; deploy.
  3. Wait ≥ the longest backend JWKS cache TTL (e.g. 24 h) so every consumer has seen the new kid.
  4. Switch the definition to sign with the new key; old key stays published until all tokens signed with it expire.
  5. Remove the old key; deploy; monitor validation errors.

⚠️ Security Pitfall — “just allow all”
The right fix for a 403/302 is a narrow allow on exactly these URLs, not any-other permissions on /mga and not disabling the WAF. Metadata/JWKS are safe to publish; the rest of /mga is not.
