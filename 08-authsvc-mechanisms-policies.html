08 · Authentication Service: Mechanisms & Policies

The /mga/sps/authsvc endpoint is where a login begins on ciam. It runs an authentication policy — an ordered set of steps, each performed by an authentication mechanism — and returns control to the OAuth flow when the user is authenticated.

1. Zero-knowledge explanation

📘 Beginner Concept — airport security lanes

A mechanism is a single checkpoint: scan the passport, scan the bag, answer questions. A policy is the route a traveller takes through those checkpoints: “domestic: bag scan only; international: passport + bag + questions”. The authentication service is the traffic controller that sends each person to the next checkpoint and finally issues a “cleared” stamp.

  • Policy: ordered mechanisms; each step can succeed, fail, or need another round-trip (page shown to user / redirect).
  • State: the service keeps per-login state server-side (cookie-referenced) between redirects.
  • Result: a populated session with the user's identity attributes, ready for /authorize to mint a code.

2. High-level architecture

🏗️ Architecture Deep Dive — one endpoint, many entry styles
The same service has: /authsvc?PolicyId=… (browser flows), /authsvc/policy/<name> (named policy), and /apiauthsvc (JSON API for native apps). In this environment the OAuth client parameter on /authsvc selects the policy/behaviour through the InfoMap rule.

3. Low-level technical sequence — orchestrating a multi-step login

Building it in LMI (verify names on your firmware)

  1. Secure Access Control → Policy → Mapping Rules: add InfoMap_partnerLoginRedirect.js (type InfoMap).
  2. Authentication → Mechanisms: create an InfoMap mechanism referencing that rule (e.g. mech_partner_login_redirect).
  3. Authentication → Policies: create partnerlink_login with a single step using that mechanism, set as the policy for the OIDC flow.
  4. Deploy pending changes; test https://test.partnerlink.enterprise.com/mga/sps/authsvc?PolicyId=urn:ibm:security:authentication:asf:partnerlink_login (policy URN pattern urn:ibm:security:authentication:asf:<name>).

Observed anti-patternNested URL: /authb/login?appId=27096415/authorize?appId=123… — two ? and no encoding
⚠️ Security Pitfall — state passthrough & malformed nested URL

Finding #1/#3. ciam sits between two OAuth relationships (portal↔ciam, ciam↔csl). Each leg needs its own state (CSRF defence) and nonce (replay defence). Forwarding the portal's value lets an attacker who controls one leg influence the other. Also, a second ? inside a URL value is parsed as part of the value or dropped depending on the parser; encode nested URLs: redirect_uri=https%3A%2F%2F…%2Fauthorize%3FappId%3D123.
