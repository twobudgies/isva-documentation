FAQ & Verification Status

Two reader types, one page. Developers get quick answers to the questions that block implementation. Product owners and architects get the “why”, the risk ranking, the go-live blockers, and an honest map of which statements on this site are standard, documented, or still to be verified on your system.

1. Developer questions

My backend has a client secret. Do I still need PKCE?

Yes. The secret proves which application is calling /token; PKCE proves the caller is the same party that started this login. They defend against different attacks: a stolen authorization code (browser extension, logs, referrer, shared device) is useless without the matching code_verifier. Current guidance (OAuth 2.0 Security BCP, OAuth 2.1) is PKCE for all clients. See Module 06.

Which token do I send to APIs: id_token or access_token?

Send the access token to APIs. The ID token is for your client only: it states who logged in. An API that accepts an ID token cannot tell whether it was issued for that API (aud is the client, not the API). See Module 01.

What exactly must my backend validate on an ID token?
  1. Signature with the JWKS key whose kid matches the header; alg pinned to RS256 (never accept none).
  2. iss equals the issuer from discovery (not localhost).
  3. aud contains your client_id.
  4. exp in the future, iat/nbf sane (≤ 60 s skew).
  5. nonce equals the one you sent.
  6. Optionally acr/amr for authentication strength.

Checklist version in the Quick Reference.

Why does the backend (not the browser) call /token?

Because only a server can keep client_secret and code_verifier private, and tokens should never pass through the browser address bar, history or logs. The browser only carries the short-lived, single-use code. See the 7-step flow.

Why is state different on the portal↔ciam and ciam↔csl legs?

ciam is the authorization server for the portal and an OAuth client of csl. Each relationship needs its own CSRF protection and replay protection. Forwarding the portal's value lets whoever controls one leg influence the other. ciam stores the portal's state, issues its own state2/nonce2 to csl, and restores the portal's value only at the end. See Module 12.

Login redirects in a loop. Where do I look first?

Capture a HAR and ask: which request first returned something unexpected, and who answered it? Akamai block page → edge; pkmslogin.form/HPDIA… → WebSEAL ACL or cookie; JSON error → OAuth runtime. Then check whether PD-S-SESSION-ID was sent on the return request. Triage tree: Module 14.

How long can I cache JWKS and metadata?

1–24 hours is typical, but always refetch once on an unknown kid (rate-limited), otherwise a key rotation breaks every new token. If the JWKS endpoint is blocked at that moment, validation fails even though cached keys still work for old tokens. See Module 07.

Do I need code changes to move to Verify SaaS?

If your backend uses a standards-compliant OIDC library with discovery: usually configuration only (issuer/discovery URL, client_id/secret, redirect URI registered in the new application). Things that do need attention: the iss/aud values, claim names you depend on, and any logic that relied on iv-user/iv-creds headers. See Module 13.

Can I test the flow without Akamai getting in the way?

Run the curl suite from the same host/egress IP as partner_portal_backend: that is the identity Akamai evaluates. Testing from a laptop proves nothing about the backend's access. Avoid bypassing the edge in production.

2. Product owner & architect questions

Why a broker at all? Why not let the portal talk to csl directly?

A broker gives the portal one issuer, one set of claims, and one token format regardless of how many upstream identity providers exist or change. It centralises policy (scopes, lifetimes, step-up), lets you add or swap IdPs without touching applications, and keeps upstream credentials/tokens away from the portal. The cost: one more critical component to secure and operate, which is exactly what the audit examines. See Module 01.

Should we fix on legacy ISVA first or go straight to Verify SaaS?

Fix #4 and #2 (and ideally #1) on legacy first if go-live precedes migration; they are small and migration timelines slip. Also it gives a clean baseline to test the SaaS tenant against (same curl suite, same HAR checks). If migration is imminent and the portal is not yet live, building the correct configuration directly in Verify and skipping legacy hardening can be reasonable. See the plan in Module 13.

What can ISVA do that Verify SaaS cannot (or does differently)?
  • Arbitrary server-side JavaScript in the login path (Rhino rules) → replaced by declarative mappings and webhooks; custom logic moves to a service you operate.
  • WebSEAL reverse-proxy SSO (junctions, iv-user/iv-creds header injection, POS ACLs) → not a SaaS feature; legacy applications that depend on it need a gateway/PEP or to be modernised to OIDC.
  • Custom authentication pages/templates → tenant branding and flows; confirm specific page-level customisations.
  • Full control of the appliance (tracing, firmware cadence) → managed service and reports.

Always confirm feature parity for your use cases with IBM documentation or support; the mapping on this site is conceptual.

What happens to logged-in users and existing tokens at cut-over?

Existing sessions and tokens are tied to the old issuer; they do not carry over. Plan for users to sign in again, keep legacy validation available for the overlap window (short token lifetimes help), and make sure sub is stable so accounts do not duplicate. A feature-flagged pilot with instant rollback is the safest approach.

Can csl stay as the authentication source after migration?

Yes. It becomes an Identity Source (OIDC or SAML federation) in the Verify tenant; users keep authenticating at csl including its MFA. You can later decide whether to move MFA or the directory into Verify. Because MFA then happens upstream only, configure the access policy to trust or re-require MFA deliberately.

Will disabling ROPC break something?

Only clients that use the password grant. Before disabling, check token-endpoint access logs for grant_type=password over a representative period, identify the callers, and migrate them to authorization code (users) or client credentials (services). If the log shows none, disabling is safe. Verify afterwards that the endpoint returns unsupported_grant_type.

How do we prove the fixes worked?

Every finding has an executable test (PKCE rejected without challenge, ROPC returns unsupported_grant_type, issuer correct, JWKS 200 from the backend host, single-use code, tampered state rejected). Keep them as a regression suite. See the verification table in Module 12 and the script in Module 14.

What about licensing, cost, data residency and audit retention?

Out of scope here and not something this documentation can answer: confirm with IBM and your compliance team (tenant region, log retention, subprocessors, support tiers). Audit/event streaming to your SIEM is covered conceptually in Module 13.
