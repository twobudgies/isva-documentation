10 · STSUU & Session Claims

The STSUU is the single data envelope that every token rule reads and writes. Understand its three parts — Principal, AttributeList, ContextAttributes — and you understand how a login becomes the claims in an id_token.

1. Zero-knowledge explanation

📘 Beginner Concept — the shipping envelope

Imagine a clipboard that travels with a package along the factory line. The top says who the package is for (Principal). A first list says facts about that person (AttributeList: email, groups). A second list says facts about this particular delivery (ContextAttributes: client, scope, IP, grant type, PKCE challenge). Each worker (rule) can read the clipboard and add lines. At the end, the lists are turned into token claims.

STSUU = Security Token Service Universal User, an XML structure (also exposed as a JavaScript object in rules). It is protocol-neutral: SAML, OAuth/OIDC and InfoMap all convert to and from it.

Structure

<stsuuser:STSUniversalUser xmlns:stsuuser="urn:ibm:names:ITFIM:1.0:stsuuser">
  <stsuuser:Principal>
    <stsuuser:Attribute name="name" type="urn:ibm:names:ITFIM:5.1:accessmanager">
      <stsuuser:Value>jdoe</stsuuser:Value>
    </stsuuser:Attribute>
  </stsuuser:Principal>

  <stsuuser:AttributeList>                       <!-- facts about the USER -->
    <stsuuser:Attribute name="email"><stsuuser:Value>jdoe@example.com</stsuuser:Value></stsuuser:Attribute>
    <stsuuser:Attribute name="partnerId"><stsuuser:Value>P-1001</stsuuser:Value></stsuuser:Attribute>
    <stsuuser:Attribute name="groups"><stsuuser:Value>buyers</stsuuser:Value><stsuuser:Value>admins</stsuuser:Value></stsuuser:Attribute>
  </stsuuser:AttributeList>

  <stsuuser:ContextAttributes>                  <!-- facts about THIS REQUEST/TRANSACTION -->
    <stsuuser:Attribute name="client_id" type="urn:ibm:names:ITFIM:oauth:request:parameter">
      <stsuuser:Value><partner_portal_clientid></stsuuser:Value>
    </stsuuser:Attribute>
    <stsuuser:Attribute name="scope" type="urn:ibm:names:ITFIM:oauth:request:parameter">
      <stsuuser:Value>openid</stsuuser:Value>
    </stsuuser:Attribute>
  </stsuuser:ContextAttributes>
</stsuuser:STSUniversalUser>
PartHoldsBecomes
PrincipalOne identity name (+ type)sub (subject) / token owner
AttributeListUser attributes (multi-valued)Claims such as email, groups (after mapping)
ContextAttributesRequest/transaction data with a type URIUsed for decisions; some types are emitted as response attributes

The type URI is what makes ContextAttributes powerful: urn:ibm:names:ITFIM:oauth:request:parameter = what the client sent; urn:ibm:names:ITFIM:oauth:response:attribute = what will be returned in the token response; other types cover OIDC claims and metadata (VERIFY exact URIs for your version).

2. High-level architecture — claim transformation lifecycle

🏗️ Architecture Deep Dive — session vs token
The ISVA session holds raw attributes from login (including any extras from csl). The STSUU copies the relevant ones for the token engine. Only attributes that survive mapping appear in the token — so “claim missing” is almost always a mapping problem, not a login problem.

3. Low-level technical sequence

Common STSUU operations in rules (JavaScript)

var name   = stsuu.getPrincipalName();                                      // "jdoe"
var email  = stsuu.getAttributeContainer().getAttributeValueByName("email"); // Java String[]; email[0]
stsuu.getAttributeContainer().setAttribute(new Attribute("tier", "urn:ibm:names:ITFIM:5.1:accessmanager", "gold"));
var cid    = stsuu.getContextAttributes().getAttributeValueByNameAndType("client_id",
               "urn:ibm:names:ITFIM:oauth:request:parameter");
stsuu.addContextAttribute(new Attribute("partner_id", "urn:ibm:names:ITFIM:oauth:response:attribute", "P-1001"));
IDMappingExtUtils.traceString(stsuu.toString());   // dumps XML to trace (do NOT leave on in production)

⚠️ Security Pitfall — over-sharing claims
Everything in the AttributeList is a candidate for the token, and JWTs are readable by anyone who holds them (and often logged). Map an explicit allowlist of claims; never include internal IDs, group DNs, raw upstream tokens, or personal data the portal doesn't need.

6. IBM Security Verify (SaaS) migration mapping

☁️ IBM Verify SaaS Equivalent
There is no STSUU to script. Identity attributes live on the user profile (and on federated identity-source attributes); you choose which attributes appear as claims in the application's OIDC attribute mapping, optionally transformed by custom attribute functions.
