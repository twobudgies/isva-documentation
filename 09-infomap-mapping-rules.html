09 · InfoMap & Mapping Rules (Rhino JavaScript)

The three custom rules that turn a generic ISVA into this specific broker: where each one runs, what objects it can touch, and annotated reference implementations that fix the audit findings.

Read this first
The code below is an annotated reference implementation of what each rule should do in this architecture, written against the ISVA mapping-rule API as documented for 10.x/11.x. It is not a copy of your production files. Diff it against your real InfoMap_partnerLoginRedirect.js, partnerauthn_pre_token_generation.js and partnerauthn_post_token_generation.js, and confirm class/type names on your firmware (marked // VERIFY).

1. Zero-knowledge explanation

📘 Beginner Concept — hooks in a factory line

ISVA is a factory line that builds tokens. At certain points you can attach a small worker — a hook — who may inspect the item, add a label, or stop the line. Those workers are written in JavaScript running on Rhino (a Java-based JS engine inside the runtime, ES5-level, no let/arrow functions/fetch).

RuleHook pointJob here
InfoMap_partnerLoginRedirect.jsAuthentication mechanism (InfoMap) in the authsvc policySend the user to csl; later validate the return
partnerauthn_pre_token_generation.jsOAuth “pre-token generation” mapping rule of the definitionLast check + enrich claims before the code/token is created
partnerauthn_post_token_generation.jsOAuth “post-token generation” mapping ruleAudit/side effects after the token exists
  • Scopes of data: Scope.REQUEST (this HTTP request), Scope.SESSION (this login), Scope.GLOBAL-style persistent stores via HVDB/KV (avoid).
  • Rule I/O: InfoMap rules read/write the context, macros, page, success. Token rules read/write an stsuu object (Module 10).
  • Fail closed: if anything looks wrong, stop the flow — never “continue anyway”.

2. High-level architecture

🏗️ Architecture Deep Dive — rule trust boundary
Rules run inside the runtime with full access to the session and token data. Anything they accept (query parameters, upstream attributes) is attacker-influenced input. Treat them like server code: validate, encode, log without secrets, and keep them in version control with peer review.

3. Low-level technical sequence

3.1 Every mapping-rule type in ISVA, and which ones this environment uses

“Mapping rule” is a family, not one thing. Each type hooks into a different part of the product and sees different objects. Knowing the family tells you where a behaviour could be hiding when something unexpected happens.

🏗️ Architecture Deep Dive — a design alternative worth knowing
Because csl is integrated through a hand-written InfoMap redirect, your rule is responsible for validating what comes back. If csl were registered as an OIDC (or SAML) federation partner, ISVA's Federation STS would validate the upstream ID token/assertion natively (signature, issuer, audience, nonce, state) and a small Federation mapping rule would only map attributes into the STSUU. That removes the riskiest custom code (the validation in 4.1). It is also the closest legacy analogue of the Verify SaaS Identity Source (Module 13).

If you operate more than one client or definition, each can carry its own rule set following the same naming pattern; the types and hooks above are identical.

3.2 Execution order: one login, five to six rule executions

The flow touches the rules in a fixed order. Note that the pre- and post-token rules fire twice: once on the front channel when the authorization code is created, and again on the back channel when the tokens are issued.

Verify on your appliance
That the pre- and post-token rules run on both /authorize and /token, and how a rule can tell the two apart, is how the project team described this deployment. It is plausible for the API Protection mapping-rule model but version-specific. Prove it with the trace test in 3.3 before relying on it.

3.3 Worked example: tell the phases apart and prove the order with a trace

Because the same rule file runs in more than one phase, every check must be phase-aware. For example PKCE’s code_challenge exists only on /authorize; on /token the proof is code_verifier. A rule that demands a challenge unconditionally will reject every token exchange.

// Shared helpers (copy to the top of both token rules; or share via importMappingRule if your version supports it: VERIFY)
var REQ = "urn:ibm:names:ITFIM:oauth:request:parameter";

function p(name) {                       // first value of a request parameter, or null
  var v = stsuu.getContextAttributes().getAttributeValueByNameAndType(name, REQ);
  return (v != null && v.length > 0) ? String(v[0]) : null;
}
function phase() {                       // VERIFY: which parameters each endpoint carries on your version
  if (p("grant_type") != null)    return "TOKEN";      // /token always carries grant_type
  if (p("response_type") != null) return "AUTHORIZE";  // /authorize carries response_type
  return "UNKNOWN";
}
function log(rule, extra) {              // one greppable line per execution, never secrets
  IDMappingExtUtils.traceString("[" + rule + "] phase=" + phase() + " user=" + stsuu.getPrincipalName() +
                                " client=" + p("client_id") + (extra ? " " + extra : ""));
}

Add one log(...) line at the top of each of the three rules (the InfoMap rule logs mode=OUT / mode=RETURN in the same style), enable the runtime trace, perform one login, then read the order back:

4. Environment deep dive — annotated code

4.1 InfoMap_partnerLoginRedirect.js

// ===== InfoMap_partnerLoginRedirect.js (reference) =====
importPackage(Packages.com.tivoli.am.fim.trustserver.sts.utilities);   // IDMappingExtUtils (VERIFY package)
importClass(Packages.com.tivoli.am.fim.trustserver.sts.utilities.IDMappingExtUtils);

var NS_REQ  = "urn:ibm:security:asf:request:parameter";   // query/form parameters of THIS request
var NS_SESS = "urn:partnerlink:login";                     // our own namespace stored in the session

function param(n)       { return context.get(Scope.REQUEST, NS_REQ, n); }
function randomUrlSafe(bytes) {                            // cryptographically strong, URL-safe
  var b = java.lang.reflect.Array.newInstance(java.lang.Byte.TYPE, bytes);
  new java.security.SecureRandom().nextBytes(b);
  return String(java.util.Base64.getUrlEncoder().withoutPadding().encodeToString(b));
}
function fail(msg) {                                       // fail closed
  IDMappingExtUtils.traceString("partnerLoginRedirect FAIL: " + msg);
  context.set(Scope.SESSION, NS_SESS, "state2", null);
  macros.put("@ERROR@", msg);
  page.setValue("/authsvc/authenticator/partner/error.html");   // custom error template (VERIFY path)
  success.setValue(false);
}

var state2 = context.get(Scope.SESSION, NS_SESS, "state2");

if (state2 == null) {
  // ---- MODE OUT: user is starting a login --------------------------------
  var client = param("client"), scope = param("scope"), portalState = param("state");
  var challenge = param("code_challenge"), method = param("code_challenge_method");

  if (client == null || client != "<partner_portal_clientid>") { fail("unknown client"); }
  else if (scope == null || ("" + scope).split(" ").indexOf("openid") < 0) { fail("openid scope required"); }
  else if (challenge == null || method != "S256") { fail("PKCE S256 required"); }          // Finding #2
  else {
    var s2 = randomUrlSafe(32), n2 = randomUrlSafe(32);                                     // Finding #1: ciam's OWN state/nonce
    context.set(Scope.SESSION, NS_SESS, "state2", s2);
    context.set(Scope.SESSION, NS_SESS, "nonce2", n2);
    context.set(Scope.SESSION, NS_SESS, "portalState", portalState);                        // restored at the end
    context.set(Scope.SESSION, NS_SESS, "challenge", challenge);

    // Finding #3: build the NESTED url with encoding and exactly one '?' per URL
    var back = "https://test.partnerlink.enterprise.com/mga/sps/oauth/oauth20/authorize"
             + "?client_id=" + encodeURIComponent(client) + "&scope=openid"
             + "&state=" + encodeURIComponent(s2);
    var url = "https://csl.example.com/authb/login"
            + "?appId=27096415"
            + "&redirect_uri=" + encodeURIComponent(back)
            + "&state=" + encodeURIComponent(s2) + "&nonce=" + encodeURIComponent(n2);

    // Redirect the browser (VERIFY: exact redirect mechanism for your InfoMap version)
    context.set(Scope.REQUEST, "urn:ibm:security:asf:response", "Location", url);
    context.set(Scope.REQUEST, "urn:ibm:security:asf:response", "status", "302");
    success.setValue(false);        // not authenticated yet; flow continues on return
  }
} else {
  // ---- MODE RETURN: browser came back from csl ---------------------------
  var gotState = param("state");
  if (gotState == null || gotState != state2) { fail("state mismatch"); }
  else {
    // read upstream-verified identity from the validated assertion/headers (VERIFY source)
    var uid = context.get(Scope.REQUEST, "urn:ibm:security:asf:request:header", "csl-user");
    if (uid == null) { fail("no upstream identity"); }
    else {
      context.set(Scope.SESSION, "urn:ibm:security:asf:response:token:attributes", "username", uid);
      context.set(Scope.SESSION, NS_SESS, "state2", null);       // single use: prevents replay
      success.setValue(true);
    }
  }
}
⚠️ Security Pitfall
Upstream identity must come from something the browser cannot forge: a signed assertion/ID token validated by ciam, or a server-to-server call to csl. A plain request header or query parameter set by the user is not proof of login.

4.2 partnerauthn_pre_token_generation.js

Runs in both the AUTHORIZE and TOKEN phases (see 3.2), so each check states the phase it applies to.

// ===== partnerauthn_pre_token_generation.js (reference) =====
importClass(Packages.com.tivoli.am.fim.trustserver.sts.utilities.IDMappingExtUtils);
importClass(Packages.com.tivoli.am.fim.trustserver.sts.utilities.OAuthMappingExtUtils);   // VERIFY
importClass(Packages.com.tivoli.am.fim.trustserver.sts.uuser.Attribute);                 // VERIFY

var REQ  = "urn:ibm:names:ITFIM:oauth:request:parameter";
var RESP = "urn:ibm:names:ITFIM:oauth:response:attribute";

function p(name) {                                   // first value or null (Java String[] -> JS string)
  var v = stsuu.getContextAttributes().getAttributeValueByNameAndType(name, REQ);
  return (v != null && v.length > 0) ? String(v[0]) : null;
}
function phase() {                                   // VERIFY (see 3.3)
  if (p("grant_type") != null)    return "TOKEN";
  if (p("response_type") != null) return "AUTHORIZE";
  return "UNKNOWN";
}
function deny(m) {
  IDMappingExtUtils.traceString("[pre-token] DENY phase=" + phase() + " reason=" + m);
  OAuthMappingExtUtils.throwSTSCustomUserMessageException(m, 400);   // VERIFY signature
}

var ph = phase();
IDMappingExtUtils.traceString("[pre-token] phase=" + ph + " user=" + stsuu.getPrincipalName() + " client=" + p("client_id"));

// 1. PKCE: the challenge exists only on /authorize; on /token the proof is the verifier
if (ph == "AUTHORIZE") {
  if (p("code_challenge") == null || p("code_challenge_method") != "S256") { deny("pkce_required"); }
} else if (ph == "TOKEN" && p("grant_type") == "authorization_code") {
  if (p("code_verifier") == null) { deny("code_verifier_required"); }
}

// 2. Scope allowlist (openid + profile only), checked where scope is present
var allowed = {"openid": 1, "profile": 1};
var scope = p("scope");
if (scope != null) {
  var parts = scope.split(" ");
  for (var i = 0; i < parts.length; i++) { if (!allowed[parts[i]]) { deny("scope_not_allowed:" + parts[i]); } }
}

// 3. Enrich claims at the TOKEN phase (where the final tokens are shaped); VERIFY if your version needs AUTHORIZE
if (ph == "TOKEN") {
  var partnerId = stsuu.getAttributeContainer().getAttributeValueByName("partnerId");
  if (partnerId != null && partnerId.length > 0) {
    stsuu.addContextAttribute(new Attribute("partner_id", RESP, String(partnerId[0])));
  }
}
// 4. NEVER copy secrets/passwords/raw upstream tokens into claims.
⚠️ Security Pitfall — the phase bug
An earlier draft of this rule demanded code_challenge unconditionally. If the rule also runs on /token, that rejects every token exchange with pkce_required even though the login was fine. Always branch on the phase before applying a check that only makes sense in one of them.

4.3 partnerauthn_post_token_generation.js

// ===== partnerauthn_post_token_generation.js (reference) =====
importClass(Packages.com.tivoli.am.fim.trustserver.sts.utilities.IDMappingExtUtils);

var REQ = "urn:ibm:names:ITFIM:oauth:request:parameter";
function p(name) {
  var v = stsuu.getContextAttributes().getAttributeValueByNameAndType(name, REQ);
  return (v != null && v.length > 0) ? String(v[0]) : null;
}
try {
  var ph = (p("grant_type") != null) ? "TOKEN" : (p("response_type") != null ? "AUTHORIZE" : "UNKNOWN");   // VERIFY
  // audit line: WHO, WHICH CLIENT, WHICH PHASE, WHEN. Do NOT log codes, tokens, secrets.
  IDMappingExtUtils.traceString("[post-token] phase=" + ph + " user=" + stsuu.getPrincipalName() +
      " client=" + p("client_id") + " " + (ph == "AUTHORIZE" ? "code issued" : "tokens issued") +
      " ts=" + new Date().toISOString());
} catch (e) {
  IDMappingExtUtils.traceString("[post-token] audit error: " + e);   // never break issuance for logging
}

Debugging tips

  • IDMappingExtUtils.traceString(msg) writes to the runtime trace — enable the trace spec for the mapping-rule component (Module 04) and turn it off afterwards.
  • Rhino ≈ ES5: use var, function, indexOf; Date.prototype.toISOString exists; no const/arrow/template strings/Promise.
  • Java arrays/strings from Java calls: wrap with String(...) before comparing.
